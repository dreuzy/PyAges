# External LPM extension audit — 2026-11-28

## Conclusion

The external-LPM editing and installation path is functional and suitable for
maintained use. A contributor can generate either a SciPy-backed or direct
NumPy model, edit it outside the PyAges repository, install it as an ordinary
Python distribution, discover it without an explicit import, validate its
integration, and construct it through the standard `build_lpm()` API.

The audit found two maintainability gaps rather than a broken runtime design:

1. several subsystem and generated-function docstrings described the result in
   one sentence without explaining lifecycle, precedence, effects, errors, or
   scientific limits;
2. maintained examples were installed end to end, but no test installed the
   untouched output of the actual `pyages new lpm` command.

Both gaps were corrected during this audit.

## Audited boundary

| Area | Primary implementation |
| --- | --- |
| Public plugin record and provenance | `pyages/lpm/extensions.py` |
| Built-in and entry-point catalogue | `pyages/lpm/core/registry.py` |
| Parameter precedence and construction | `pyages/lpm/factory.py` |
| Fast deterministic integration check | `pyages/lpm/checks.py` |
| YAML parameter contract | `pyages/data_io/_lpm_parameter_schema.py` |
| CLI project generation | `pyages/cli/templates/lpm_template.py` and `_lpm_sources.py` |
| User commands | `pyages new lpm`, `pyages list lpms`, and `pyages check lpm` |
| Maintained reference packages | `examples/templates/external_lpm_plugin*` |

The audit did not reassess the scientific validity of a particular groundwater
transit-time distribution. That remains the responsibility of model-specific
analytical tests, independent reference data, and study review.

## Verified lifecycle

```text
pyages new lpm NAME --layout plugin --base scipy|root
        |
        v
standalone project: code + params.yaml + tests + pyproject.toml
        |
        v
pip installation records one pyages.lpms entry point
        |
        v
pyages list lpms reads metadata without importing plugin code
        |
        v
build_lpm(NAME) loads and validates only the selected provider
        |
        v
factory applies parameter-root precedence and attaches provenance
        |
        v
pyages check lpm NAME exercises the shared numerical contract
```

Four real-package cases exercise this lifecycle in fresh temporary paths:

- the maintained SciPy-backed `gamma_mean` example;
- the maintained NumPy-only `bounded_power` example;
- an untouched SciPy project freshly generated by the CLI;
- an untouched direct-NumPy project freshly generated by the CLI.

Each case builds and installs without network dependency resolution, appears in
`pyages list lpms`, passes `pyages check lpm`, constructs through `build_lpm`,
records the expected provider provenance, and passes its installed package
tests.

## Functional findings

### Discovery and conflicts

- Built-in registration and external entry-point metadata share one catalogue.
- Listing external models is lazy: it does not call the entry point's `load()`.
- A built-in/external or external/external duplicate name becomes unavailable;
  PyAges reports every provider instead of selecting by installation order.
- Invalid names, import failures, incompatible API versions, wrong definition
  types, wrong model bases, and missing packaged parameter files produce focused
  errors at the plugin boundary.
- Loaded definitions are cached for the process. Changing installed entry-point
  metadata requires a process restart, as documented.

### Construction and parameters

- An explicit parameter root takes precedence over provider-packaged data.
- Model construction parses the same version-1 YAML schema for built-in and
  external models.
- Parameter names, finite calibration ranges, mathematical domains, starts,
  optional proposal steps, and supported priors are validated centrally.
- The factory rejects a provider whose constructed model name differs from the
  advertised entry-point name.
- Provenance records provider distribution and version, entry-point target, API
  version, and the SHA-256 digest of the exact parameter file used.

### Generated projects

- Both `scipy` and `root` variants generate executable model code rather than
  placeholder methods.
- Package metadata includes the entry point and `params.yaml` package-data rule.
- Publication is atomic for plugin layout: files are staged in a sibling
  temporary directory and renamed only after all writes succeed.
- An existing plugin destination is not merged or overwritten.
- Generated comments and README text distinguish mathematical domains from
  finite calibration ranges and distinguish integration checking from
  scientific qualification.

### Integration checker

The deterministic checker reports rather than hides construction and numerical
failures. It covers:

- construction and provenance;
- initial and calibration-midpoint parameter vectors;
- convolution-strategy method requirements;
- finite non-negative mean and standard deviation;
- ordered non-negative quantiles;
- shape-preserving finite PDF and CDF results;
- non-negative density, CDF bounds, monotonicity, practical normalization, and
  CDF/quantile consistency;
- cumulative partial-moment consistency for continuous models;
- production convolution against analytically predictable constant and affine
  tracer responses.

It intentionally does not prove behavior over the complete parameter domain or
the scientific relevance of a law.

## Documentation findings and changes

The documentation now exists at four complementary levels:

1. `external-lpm-quickstart.md` gives the shortest task-oriented path and
   explains parameter syntax;
2. `external-lpm-models.md` documents entry points, loading, conflicts,
   provenance, security, and checker coverage;
3. both maintained package READMEs explain their editable files, formulas, and
   scientific tests;
4. implementation docstrings explain the behavior adjacent to the code.

Docstrings were expanded across the public records, registry, factory, checker,
parameter schema, generator, generated code, maintained examples, CLI commands,
and example tests. The revised text now explains where appropriate:

- what a function is responsible for and what it deliberately defers;
- parameters and returned records;
- filesystem or process-cache effects;
- precedence and lazy-loading behavior;
- raised exceptions or report-based failure behavior;
- the difference between technical integration and scientific qualification.

## Residual limits and recommendations

| Limit | Consequence | Recommendation |
| --- | --- | --- |
| Entry-point loading executes third-party Python | An installed plugin is a trust boundary | Install only reviewed packages and dependencies |
| The checker uses two deterministic parameter vectors | Passing does not cover extreme or limiting regimes | Add model-owned parametrized analytical tests |
| Generated mathematics is demonstrative | Immediate execution is not scientific qualification | Replace or justify formulas, ranges, priors, and tolerances |
| Discovery is cached per process | Newly installed or edited entry-point metadata may not appear immediately | Restart the Python or CLI process |
| The template uses setuptools packaging | Alternative build backends are outside the maintained example | Retain the entry-point and package-data contract if changing backend |
| Source layout writes model and central YAML separately | Declining one overwrite can leave only the other file updated | Prefer plugin layout for independently maintained models |

No additional abstraction is recommended now. The current small
`LpmDefinition` record and ordinary Python packaging metadata keep the external
author surface readable; hiding them behind more dynamic discovery would make
execution, conflicts, and reproducibility harder to inspect.
